# Описание системы вывода НПА на сайте

## 1. Введение

Данная система предназначена для отображения нормативно-правовых актов (НПА) на веб-сайте Законодательного Собрания города Севастополя. Она позволяет пользователям просматривать текст документа с учётом всех исторических редакций, сравнивать редакции между собой, просматривать историю изменений отдельных структурных элементов (статей, пунктов, таблиц и т.д.) и скачивать документ в формате RTF.

Система построена по принципу клиент-серверной архитектуры с использованием:
- **PHP** (серверная логика, работа с БД, генерация HTML и JSON),
- **JavaScript** (интерактивность на клиенте: модальные окна, дерево оглавления, выделение различий, скачивание),
- **CSS** (оформление, адаптивность).

Все компоненты тесно интегрированы и обеспечивают единый пользовательский интерфейс для работы с НПА.

## 2. Архитектура системы

### 2.1. Общая структура взаимодействия

```
[Браузер] ↔ [MODX (CMS)] ↔ [PHP сниппет] ↔ [MySQL БД]
                     ↕
              [статический HTML-кеш]
```

- **PHP-сниппет** — единый скрипт `src/site/php/snippet.php`, который автоматически собирается из модулей `src/site/php/npazs/` командой `make build-snippet` (`data/work_tools/build_snippet.py`). Модули — источник истины (их правит ИИ-агент), собранный файл — артефакт сборки (не редактируется вручную); его содержимое вставляется в сниппет `HtmlFromNpaZS` в БД MODX Evolution, как и раньше. Карта модулей и правила для агентов — в `src/site/php/npazs/README.md`; прежний монолит — в git-истории и в копии `data/debug_runs/snippet_monolith_backup.php`.
- **JavaScript** (файл `НОВЫЙ СКРИПТ.txt`, репозиторий: `src/site/js/npa-viewer.js`) — клиентская логика, работающая после загрузки страницы. Она использует встроенные данные (`<script id="npa-static-data">`) для реализации интерактивных функций без дополнительных запросов к серверу.
- **CSS** (файл `НОВЫЕ СТИЛИ.txt`, репозиторий: `src/site/css/npa-styles.css`) — определяет внешний вид всех элементов: типографику, кнопки, модальные окна, выделение изменений, оглавление и адаптивность под мобильные устройства.

### 2.1.1. Структура PHP-кода (модули и сборка)

Порядок секций задаёт точка входа-«рецепт» `src/site/php/npazs/HtmlFromNpaZS.php`; сборщик `data/work_tools/build_snippet.py` разворачивает в монолит каждый `require` и переносит секции дословно: bootstrap (.env) → модули-функции → контекст запроса (`npa_id`, TV) → дата просмотра и PDO → AJAX-диспетчер (`ajax.php`) → сборка страницы. Модули по зонам ответственности: `bootstrap.php` (.env), `helpers/` (даты, текст), `cache/` (статический кеш), `revisions/` (редакции элементов/заголовков/номеров, контекст выбранной редакции), `document/` (статус, наименование), `descriptions/` (НПА-источники изменений), `content/` (контент, таблицы, сравнение), `ui/` (кнопки, примечания, селектор, подпись), `render/` (дерево, рекурсивный рендер элементов), `history/` (таймлайны для модалок). Подробная таблица с функциями, правила сборки и проверки — `src/site/php/npazs/README.md`.

### 2.2. Кэширование

Для ускорения загрузки система кэширует готовый HTML-код документа в статические файлы. Путь к файлу строится по шаблону:

```
/assets/npa/{тип_нпа}/{год}/{npa_id}/{npa_id}_{дата_просмотра}.html
```

При повторном запросе на ту же дату, если файл существует и не передан параметр принудительной регенерации (`regenerate`, `force`), сервер отдаёт содержимое кэша, минуя тяжёлые операции с БД.

## 3. Структура базы данных (основные таблицы)

Система использует набор таблиц, обеспечивающих хранение структуры документа, редакций и истории изменений. Ниже приведены ключевые таблицы, используемые в сниппете.

### 3.1. Основные таблицы

| Таблица | Назначение |
|--------|------------|
| `npa_base` | Основная информация о документе: `npa_id`, тип (`law`/`regulation`), номер, дата принятия, дата утраты силы, формат даты, URL и пр. |
| `npa_law` / `npa_regulation` | Специфические поля для законов и постановлений (дата подписания, номер сессии, созыв и т.д.). |
| `npa_item` | Структурные элементы документа (статьи, главы, пункты, таблицы и т.д.). Содержит `id`, `npa_id`, `parent_id`, `item_id` (внешний идентификатор), `item_type`, `item_number`, `sort_order`. |
| `npa_item_revision` | Редакции содержимого элемента. Поля: `rev_id`, `item_internal_id`, `valid_from`, `valid_to`, `mod_type` (add/change/new_redaction/delete), `modified_by_id` (ссылка на элемент-источник изменения), `highlights` (JSON с данными для подсветки различий), `not_valid`. |
| `npa_item_head_revision` | Редакции заголовка элемента. Аналогично `npa_item_revision`, но хранит `head_text`. |
| `npa_head_revision` | Редакции наименования всего документа. |
| `npa_item_number_revision` | Редакции номера элемента (используется для отображения правильного номера на определённую дату). |
| `npa_item_prefix_revision` | Редакции префикса для приложений (например, «Приложение к постановлению...»). |
| `npa_paragraph` | Параграфы (абзацы, таблицы, фрагменты) внутри редакции элемента. Связаны с `rev_id`, содержат `block_type` (paragraph, table, table_fragment, child_ref), `html_text`, `sort_order`. |
| `npa_revision_info` | Информация о редакциях документа (изменениях, внесённых другими НПА). Содержит `revision_date_valid`, `revision_number`, `revision_url`. |
| `npa_signatory` | Подписанты документа (должность, ФИО). |
| `person` / `person_post` | Справочники лиц и должностей. |
| `npa_note_unified` | Примечания к документу или его элементам. |

### 3.2. Ключевые связи

- `npa_item.parent_id` → `npa_item.id` (иерархия элементов).
- `npa_item_revision.item_internal_id` → `npa_item.id`.
- `npa_item_revision.modified_by_id` → `npa_item.id` (ссылка на элемент документа, которым было внесено изменение).
- `npa_paragraph.rev_id` → `npa_item_revision.rev_id`.
- `npa_head_revision.npa_id` → `npa_base.npa_id`.

## 4. Серверная часть (PHP)

### 4.1. Общий алгоритм работы

1. **Получение параметров**  
   - `npa_id` – идентификатор документа (передаётся через TV-параметр или GET).  
   - `view_date` – дата, на которую показывается документ (из URL). Если не задана, берётся максимальная дата из всех редакций.  
   - Параметры принудительной регенерации (`regenerate`, `force`).

2. **Определение даты просмотра**  
   Датой просмотра считается либо переданный `view_date`, либо последняя известная дата изменения документа (`max(valid_from)` из `npa_base` и `npa_revision_info`). `view_date` остаётся датой исторического среза документа, но больше не является единственным критерием выбора структурной редакции.

3. **Определение контекста выбранной редакции**  
   По `npa_id` и `view_date` определяется выбранная редакция документа через `npa_revision_info`. Полученный набор `revision_id` сохраняется в `selected_revision_npa_ids` и передаётся во все функции, которые формируют текущее состояние структурных элементов, заголовков, номеров, префиксов, истории и сравнения.

4. **Проверка кэша**  
   Если статический HTML-файл для данной даты существует и не запрошена регенерация, содержимое файла возвращается напрямую.

5. **Загрузка данных из БД**  
   - Получение основной информации о документе (`npa_base`, `npa_law`/`npa_regulation`).  
   - Определение статуса документа (действует/утратил силу/вступает в силу).  
   - Получение редакций заголовка документа (`npa_head_revision`).  
   - Получение списка всех элементов документа (`npa_item`) и их актуальных редакций на дату просмотра.  
   - Построение дерева элементов (`getItemTree()`).  
   - Загрузка примечаний к документу и элементам.  
   - Получение активных редакций документа (`npa_revision_info`).

6. **Генерация HTML-содержимого**  
   - Рендеринг заголовка документа, даты, подписей.  
   - Рендеринг структурных элементов (рекурсивный обход дерева) с учётом их типа и редакции.  
   - Вставка интерактивных кнопок (история, сравнение, предыдущая редакция).  
   - Добавление примечаний и служебных блоков.

7. **Формирование статических данных для клиента**  
   Для каждого элемента и его редакций предварительно генерируются:
   - Содержимое выбранной редакции (HTML).  
   - История изменений (список редакций с датами и источниками).  
   - Данные для сравнения (предыдущая и текущая редакция, выделения).  
   Все эти данные упаковываются в JSON и вставляются в скрытый тег `<script id="npa-static-data">`.

8. **Сохранение в кэш**  
   Сгенерированный HTML (вместе со скриптом) сохраняется в файл.

9. **Вывод**  
   Возвращается готовый HTML-код для вставки в MODX.

### 4.2. Важные функции и классы

| Функция | Назначение |
|--------|------------|
| `getItemTree()` | Строит дерево элементов с учётом `view_date` и контекста выбранной редакции. Если структурная редакция внесена именно выбранным изменяющим НПА, она может быть использована даже при `valid_from > view_date`. |
| `renderElement()` | Рендерит один элемент документа (статью, пункт, таблицу и т.д.) в HTML. Учитывает тип, номер, заголовок, параграфы и дочерние элементы. |
| `renderSubtree()` | Рекурсивно обходит поддерево элементов и вызывает `renderElement()` для каждого. |
| `getRevisionForDate()` | Возвращает обычную редакцию элемента, действующую на указанную дату. Базовая функция исторического среза не изменяет свою семантику. |
| `getRevisionForSelectedEdition()` | Определяет редакцию элемента для выбранной редакции НПА: сначала учитывается обычный исторический срез, затем — редакция, непосредственно внесённая выбранным изменяющим НПА, даже если её `valid_from` позже `view_date`. |
| `getItemHeadRevisionForSelectedEdition()` | Аналогично определяет заголовок элемента в контексте выбранной редакции. |
| `getItemRevisionTimelineForSelectedEdition()` | Формирует историю редакций элемента относительно фактически выбранной редакции, не включая изменения последующих НПА. |
| `getItemHeadRevisionTimelineForSelectedEdition()` | Формирует аналогичную историю для заголовка элемента. |
| `getItemCompareForSelectedEdition()` / `getItemHeadCompareForSelectedEdition()` | Формируют сравнение текущей выбранной редакции с предыдущей редакцией в её цепочке. |
| `getShortNpaDescription()` | Возвращает описание НПА, которым было внесено изменение (используется в заметках). |
| `normalizeHighlights()` | Приводит данные о выделении различий к стандартному формату. |
| `renderSignature()` | Генерирует HTML-блок с подписью и реквизитами. |
| `getHeadCompareHtml()` / `getItemHeadCompareHtml()` | Формируют данные для сравнения двух редакций заголовка (документа или элемента). |
| `generateFilename()` | Генерирует имя файла для скачивания RTF на основе реквизитов документа. |

### 4.3. Особенности рендеринга

- **Типы элементов** (`item_type`): `preamble`, `chapter`, `section`, `article`, `part`, `point`, `subpoint`, `appendix`, `nested_appendix`, `structured_table`.
- Для элементов типа `part`, `point`, `subpoint` номер элемента вставляется непосредственно перед текстом первого параграфа с автоматическим добавлением точки/скобки, если необходимо.
- Для таблиц (`structured_table`) используется специальный рендеринг: таблица собирается из фрагментов (`table_fragment`), которые могут быть вложены через ссылки на дочерние элементы (`child_ref`).
- Для каждого элемента могут генерироваться кнопки:
  - «Предыдущая редакция» (если в цепочке выбранной редакции есть предыдущая).
  - «История изменений».
  - «Сравнение редакций» (если для выбранного состояния доступно сравнение с предыдущей редакцией).
- Кнопки используют тот же контекст `selected_revision_npa_ids`, что и отображаемый текст элемента. Поэтому текст, история, предыдущая редакция и сравнение не должны обращаться к разным временным срезам.
- Для отложенных изменений кнопки работают относительно фактически выбранной структурной редакции, а не только относительно `view_date`.
- Кнопки оборачиваются в `<div class="npa-item-buttons">`, который по умолчанию скрыт и показывается по клику на иконку рядом с заметками.
- Сравнение редакций родительского элемента выполняется **рекурсивно по всему поддереву**: в обеих колонках модального окна отображаются предыдущая и текущая редакции не только тела самого элемента, но и всех его дочерних элементов на всех уровнях вложенности. «Текущая» колонка рендерится на актуальную дату просмотра (`view_date`), поэтому изменения, внесённые только в дочерние элементы после последней редакции родителя (при которых у родителя в БД отдельная редакция не создаётся), также отображаются и подсвечиваются в сравнении.

### 4.4. Работа с датами

- Все даты хранятся в формате `Y-m-d`. На вход могут поступать как `Y-m-d`, так и `d.m.Y` (парсинг через `parseDate()`).
- Для отображения дат используется функция `formatRusDate()`, которая возвращает дату в формате «12 января 2024 года» с учётом падежей.
- При выборе даты просмотра (`view_date`) система формирует базовый исторический срез документа.
- Дополнительно определяется изменяющий НПА, соответствующий выбранной редакции (`selected_revision_npa_ids`).
- Если элемент был изменён именно этим НПА и его `valid_from` позже `view_date`, такая редакция всё равно отображается как часть выбранной редакции.
- Изменения, внесённые последующими изменяющими НПА, в выбранную редакцию не попадают.
- Поэтому дата `valid_from` конкретного элемента может быть позже даты общей редакции документа. Это нормально: в самом элементе/примечании отображается фактическая дата вступления его изменения в силу.

## 5. Клиентская часть (JavaScript)

### 5.1. Структура и загрузка данных

При загрузке страницы скрипт выполняет:

1. `loadStaticData()` – парсит содержимое `<script id="npa-static-data">` и сохраняет в глобальные переменные `NPA_STATIC_DATA` и `NPA_NO_NAME_IDS`. В статических данных для редакционных операций также учитывается контекст выбранной редакции.
2. `filterInvalidButtons()` – скрывает кнопки, для которых нет данных (например, если у элемента нет предыдущей редакции).
3. Инициализация оглавления (TOC) – создание кнопки и панели с деревом.
4. Инициализация переключателей (toggle-иконок) для показа/скрытия кнопок — `initToggleButtons()` (см. механизм ниже).
5. Форматирование заголовков элементов (вынос номера в отдельный класс) – `initNPAHeadings()`.
6. Обработка номеров структурных элементов (`initStructNumbers()`).
7. Синхронизация селектора редакций с URL (`syncSelectWithUrl()`).
8. Обновление подписи к кнопке скачивания RTF (`updateRtfCaption()`).
9. Назначение обработчиков кликов на кнопки элементов.

**Механизм показа кнопок (`initToggleButtons()`)**

Контейнер кнопок `.npa-item-buttons` скрыт по умолчанию (`display:none` в CSS) и показывается только по клику на иконку `.toggle-buttons-icon`, которая встраивается в заметку о редакции. Поскольку PHP может выводить контейнер кнопок **не соседним** элементом после заметки (например, когда у элемента менялось наименование: контейнер кнопок заголовка выводится *перед* заметкой элемента, а заметка заголовка при этом может отсутствовать вовсе), привязка иконок выполняется в три прохода:

1. **Проход 1**: для каждой заметки (`.element-revision-notes`, `.head-revision-notes`, `.document-revision-note`) ищется ближайший следующий контейнер `.npa-item-buttons` (просмотр останавливается на следующей заметке) — иконка встраивается в заметку.
2. **Проход 2**: «сироты» — контейнеры, оставшиеся без иконки (стоят перед своей заметкой и т.п.), привязываются к ближайшей **предыдущей** заметке в том же родителе.
3. **Проход 3**: гарантия доступности кнопок — если иконку привязать так и не удалось, standalone-иконка создаётся непосредственно перед контейнером.

Повторный вызов функции безопасен: уже привязанная иконка (метка `_npaBound`) не биндится повторно, а существующая в заметке иконка без обработчика (например, в уже трансформированном DOM) перепривязывается к контейнеру вместо создания дубликата.

### 5.2. Основные клиентские функции

| Функция | Назначение |
|--------|------------|
| `npaShowModal(title, contentHtml, skipFormatting)` | Открывает модальное окно с заданным заголовком и содержимым. При необходимости форматирует внутренние заголовки и структуру. |
| `npaCloseModal()` | Закрывает модальное окно. |
| `npaFetchRevision(revId, itemId, npaId, titlePrefix, sourceText, context)` | Загружает и отображает конкретную редакцию элемента или заголовка в модальном окне. |
| `npaShowHistory(itemId, npaId, context)` | Отображает историю изменений элемента (или заголовка) в модальном окне. По клику на кнопку «Просмотреть» открывается конкретная редакция. |
| `npaShowCompare(itemId, npaId, context)` | Отображает сравнение двух последних редакций элемента (или заголовка) в модальном окне с двумя колонками и синхронизацией прокрутки. |
| `npaGetViewDateSql()` | Возвращает выбранную дату просмотра в формате `Y-m-d`: из `NPA_STATIC_DATA.view_date`, а при её отсутствии — текущую дату. |
| `npaIsRevExpiredForView(validTo)` | Определяет, утратила ли редакция силу **относительно даты просмотра**: `true` только если `valid_to < view_date`. Используется в модалках истории для подписи «по …» и флага `isExpired`. |
| `applyPreciseHighlights(oldHtml, newHtml, highlights, modType, rootItemId, context, parentCompareData)` | Применяет выделения к HTML двух редакций для отображения различий (вставки, удаления, изменения). Вызывает внутренние функции для работы с текстовыми узлами и таблицами. |
| `npaDownloadRtf()` | Генерирует и скачивает RTF-файл документа. Создаёт клон содержимого, применяет форматирование, преобразует в RTF и инициирует загрузку. |
| `npaChangeRevision(value)` | Изменяет дату просмотра документа через GET-параметр `view_date` и перезагружает страницу. |

### 5.3. Оглавление (TOC)

Реализовано как выдвижная панель с деревом элементов.

- **Кнопка** — фиксированная кнопка в правом нижнем углу. Появляется после загрузки дерева.
- **Панель** — выезжает справа (на мобильных — на всю ширину). Содержит дерево с возможностью сворачивания/разворачивания узлов.
- **Дерево** строится на основе данных из HTML-структуры (классы `.toc-list`, `.toc-item`, `.toc-link`). Для узлов с дочерними элементами добавляется кнопка-переключатель (`▶`/`▼`).
- **Навигация**: клик по ссылке в оглавлении плавно прокручивает страницу к соответствующему элементу и подсвечивает ссылку.
- **Адаптивность**: на мобильных устройствах панель занимает весь экран, кнопка перемещается в левый нижний угол.

### 5.4. Выделение различий (diff)

Для сравнения двух редакций используются следующие подходы:

- **Текстовые выделения**: на основе JSON-данных из `highlights` для каждого элемента формируются правила (фраза, позиция, тип). Скрипт находит соответствующие фрагменты в тексте и оборачивает их в `<span>` с классами:
  - `npa-diff-insert` – вставка (зелёный фон).
  - `npa-diff-delete` – удаление (красный фон, зачёркнутый текст).
  - `npa-diff-difference` – изменение (оранжевый фон).
  - Элементы с одинаковым `data-pair-id` подсвечиваются одинаковым цветом при наведении (связь между удалённым и вставленным фрагментами).

- **Блочные выделения**: для целых элементов (например, добавление/удаление статьи) используются обёртки `<ins>` и `<del>` с соответствующими классами.

- **Таблицы**: строки таблиц могут быть выделены целиком с помощью классов `npa-diff-insert` и т.д., применяемых к `<tr>`.

- **Вложенные элементы**: сравнение редакций родительского элемента строится по всему его поддереву — в HTML сравнения включаются все дочерние элементы рекурсивно. Выделение каждого дочернего блока применяется рекурсивно; изменение блока считается релевантным, если его собственный контент (без учёта вложенных блоков) реально отличается между колонками «предыдущая» и «текущая».

### 5.5. Форматирование заголовков и номеров

На клиенте выполняется дополнительное форматирование для улучшения внешнего вида:

- Заголовки элементов (`Статья 1. ...`, `Глава 2. ...`, `Раздел 3. ...`) преобразуются в структурированный HTML с разделением номера и названия (`<span class="npa-article-num">` и `<span class="npa-article-title">`).
- Для пунктов, подпунктов и частей номер вставляется как отдельный элемент с классом `npa-struct-num` перед текстом первого параграфа.
- Для таблиц и приложений обрабатываются префиксы и заголовки.

### 5.6. Работа с RTF

Функция `npaDownloadRtf()` выполняет:

1. Клонирует содержимое документа (`.npa-doc-content`) и удаляет нежелательные элементы (кнопки, скрипты, якоря).
2. Форматирует заголовки: объединяет номер и название в одну строку, если название короткое.
3. Генерирует RTF-код с помощью внутреннего парсера `_npaGenerateRtf()`, который рекурсивно обходит DOM и преобразует теги и стили в команды RTF (шрифты, отступы, таблицы, гиперссылки).
4. Создаёт Blob и инициирует скачивание.

## 7. Взаимодействие компонентов (пошагово)

1. **Пользователь открывает страницу документа**.
2. PHP-сниппет определяет дату просмотра (из URL или последнюю), загружает данные из БД, строит HTML и JSON, сохраняет в кэш, выводит результат.
3. Браузер загружает HTML, CSS и JavaScript.
4. JavaScript инициализируется:
   - Парсит статические данные.
   - Настраивает кнопки, оглавление, переключатели, форматирование.
   - Синхронизирует селектор редакций с URL.
5. Пользователь взаимодействует с элементами:
   - Нажимает на иконку-переключатель рядом с заметками → появляются кнопки.

   - Меняет выбор в селекторе редакций → страница перезагружается с параметром `view_date`.
   - Нажимает «Скачать RTF» → генерируется и скачивается RTF-файл.

## 8. Дополнительные механизмы

### 8.1. Номера и префиксы

- Номера элементов могут меняться со временем. Для этого существует таблица `npa_item_number_revision`. При рендеринге на дату используется актуальный номер.
- Для приложений может быть префикс (например, «Приложение к постановлению...»), который также имеет свои редакции (`npa_item_prefix_revision`).

### 8.2. Элементы без названия (no_name)

Некоторые разделы (например, внутри приложений) могут не иметь префикса «Раздел». Это регулируется через поле `no_name` в `npa_base`, где перечислены `item_id` таких элементов. На клиенте и сервере это учитывается при формировании заголовков.

### 8.3. Обработка утративших силу элементов

- Элемент, утративший силу, отображается с пометкой «Утратил(а/о) силу».
- Вместо содержимого показывается ссылка «Посмотреть текст ...», которая открывает последнюю редакцию в модальном окне.
- Все изменения, внесённые после утраты силы, игнорируются (элемент не отображается в дереве на более поздние даты).

**Семантика «утраты силы» относительно даты просмотра (важно!).** Признак «элемент/редакция утратил(а) силу» вычисляется не абсолютно, а относительно **выбранной даты просмотра** (`view_date` / `asOfDate`):

- Редакция считается действующей на дату просмотра, если у неё нет `valid_to` либо `valid_to >= view_date`.
- Редакция считается утратившей силу, только если `valid_to < view_date` (либо проставлен `not_valid` при отсутствии `valid_to`).
- Эталонная логика — `isRevisionCurrent()`: `(is_null($validTo) || $validTo >= $asOfDate)`.
- Эта семантика применена во **всех** местах, где вычисляются флаги `is_current` / `is_expired`:
  - предвычисление историй элементов и заголовков для статического JSON (блоки `precomputed.histories`, ~строки 4240, 4359, 4496 сниппета);
  - «списочные» сборщики историй для AJAX-модалок (`getItemRevisionsList`, `getHeadRevisionsList`, `getItemHeadRevisionsList`, параметр `$asOfDate`);
  - на клиенте — хелпер `npaIsRevExpiredForView(validTo)`, сравнивающий `valid_to` с `NPA_STATIC_DATA.view_date`.

Благодаря этому при просмотре исторической редакции документа (например, в редакции закона 459-ЗС) элемент, который был изменён в этой редакции, но утратил силу **позже** (в последующих правках), показывается как действующий: кнопки «Предыдущая редакция / История изменений / Сравнение редакций» у него доступны, а последняя редакция в таймлайне на дату просмотра помечается `is_current = true`.

### 8.4. Примечания к элементам

- Примечания могут быть привязаны как к документу в целом, так и к отдельным элементам. Они отображаются в виде иконки с текстом внутри блока элемента.
- Примечание к элементу отображается только если его `valid_to` не задан (бессрочно) **или** `valid_to >=` даты вступления в силу выбранной редакции (`view_date`). Примечание, у которого `valid_to` меньше даты вступления в силу выбранной редакции, считается истёкшим и не выводится (см. `docs/db_schema.md` §6.1.4). Фильтрация выполняется дважды: в SQL-запросе примечаний в точке входа (`HtmlFromNpaZS.php`) и при рендере элемента (`render/element.php` → `filterNotesByValidTo()` в `ui/notes.php`).

## 8.5. Правила отображения редакций

Для реализации версионности действуют следующие правила:

1. Выбор редакции документа не изменяет смысл `view_date`: он продолжает задавать базовую историческую дату.
2. Для выбранной редакции дополнительно определяется изменяющий НПА через `npa_revision_info`.
3. Структурная редакция, внесённая выбранным НПА, имеет приоритет для отображения соответствующего элемента, даже если её `valid_from` позже `view_date`.
4. Изменения последующих НПА не включаются в состояние выбранной редакции.
5. История, предыдущая редакция и сравнение используют тот же контекст выбранной редакции, что и основной текст.
6. Фактическая дата вступления в силу структурного изменения сохраняется и отображается отдельно; она не подменяется датой общей редакции документа.
7. Такая логика применяется не только к тексту элемента, но также к его заголовку, номеру и префиксу там, где для них существуют отдельные редакции.

## 9. Безопасность и производительность

- **Кэширование**: существенно снижает нагрузку на БД и ускоряет загрузку.
- **Экранирование**: все данные, выводимые в HTML, проходят через `htmlspecialchars()`. JSON экранируется (`JSON_HEX_TAG`).
- **Ограничение глубины**: рекурсивные функции имеют ограничение глубины (20 уровней) для предотвращения переполнения стека.
- **Подготовленные запросы**: все SQL-запросы используют PDO с параметрами для защиты от инъекций.
- **Минимизация запросов**: данные для клиента предзагружаются, чтобы избежать дополнительных AJAX-запросов (за исключением случаев, когда данные не были предварительно сгенерированы).
